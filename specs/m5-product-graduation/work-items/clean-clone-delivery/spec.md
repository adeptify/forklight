and complete setup, run a real bounded Task, expose independent verification and Main review, apply
the accepted Candidate safely, and prove restart recovery. Timing is recorded as experience
evidence and never used to cancel valid work.

## Focused audit and execution decision

The 2026-08-19 source audit found no prerequisite product-code gap. The existing clean bundle
already runs prepack/full check, scans the tarball by filename, installs into an isolated prefix,
loads the installed CLI and MCP over a real protocol handshake, compares packaged/installed/
Daemon build identity, and owns exact Hub/Daemon cleanup. M5-A1 has activated CLI setup and Main
installation; M5-A2 has activated backup preview/create/inspect/restore. The source full check is
3,140/3,140 and client/Daemon identity is matched.

A3 therefore begins as one evidence-producing installed-product journey, not as a speculative
clean-run framework rewrite. It may update product code only if that exact journey exposes a
reproducible acceptance blocker. Main must first record the blocker, minimum affected call chain
and focused test here before dispatching a code Candidate. A slow but progressing Worker, an
unfamiliar-human gap reserved for M5-C, or a desire for more automation is not a code blocker.

The technical bundle and this current-user delivery remain distinct evidence. The installed run
uses a new npm prefix and `FORKLIGHT_HOME`, while reusing the current operator's already healthy
local Runtime sign-in. It must state that this is not a new macOS user, disposable VM or unfamiliar
developer observation and must never copy auth files or credential values into the bundle,
project, Task or evidence.

### 2026-08-19 blocker amendment — duplicate post-stop PID check

Two fresh bundle destinations repeated the same terminal `cleanup-failed` after the installed
lifecycle. A separate installed-prefix diagnostic then proved the same exact Hub exits immediately
and public `daemon stop` returns authoritative success with the old PID gone in one second. The
bundle cleanup currently calls that public stop and then always probes/signals the stored numeric
PID again. Once public stop has proved that old PID and socket gone, that number no longer carries
ownership and may already identify an unrelated process. This duplicate check can therefore create
both a false bundle failure and a wrong-process signal.

The minimum product recovery may change only
`src/clean-run/build-clean-run-bundle.ts` and `tests/clean-run-bundle.test.ts`. A parsed
authoritative `Daemon stopped` result ends Daemon cleanup without another numeric-PID signal.
Missing, not-running or failed stop truth retains the current exact recorded-PID fallback. Focused
tests must prove both the PID-reuse non-signal case and the still-owned fallback case. Do not change
the public Daemon timeout, add process-name scans, replay bundle publication, or widen lifecycle
semantics without new evidence. After normal verification, two different-view Judges and safe
Integration, run one new clean bundle destination; the two failed destinations remain immutable
evidence rather than favorable rerun samples.

### 2026-08-19 post-fix stop — diagnosis required before more behavior

The exact recovery completed ForkLight verification, two usable Judges, safe Integration and a
3,143/3,143 full check. The one admitted post-fix bundle destination nevertheless repeated the same
`cleanup-failed` terminal and published nothing. The current projection hides the prior
verification failure and combines Hub/Daemon cleanup into one message, so it cannot establish
which accepted assumption was wrong.

This Work Item is stopped under the no-loop rule. Do not run a fourth bundle or change cleanup
behavior from the same evidence. Any continuation must first be a separately accepted
diagnostic-only amendment with bounded, privacy-safe output for the prior verification category and
the final `hubGone`/`daemonGone` results. It must not add retry, extend timeouts, scan processes,
publish a failed bundle, start Hub UI, or treat diagnostic output as A3 graduation.

Main has now admitted that amendment at
`specs/m5-product-graduation/work-items/clean-bundle-diagnosis/spec.md` under 一骏's standing
authorization to continue later Work Items. It is serial and may change only the clean-run builder
plus its focused test. After its normal quality chain and safe Integration, Main may run exactly one
new external destination to collect the bounded diagnostic facts. No behavior recovery is implied
or pre-authorized by that result.

### 2026-08-19 root-cause amendment — staging-derived socket path is unreadable

The diagnostic Task completed two Judges, Main Integration and 3,147/3,147 full tests. Its single
external run reported `prior=daemon-identity-mismatch cleanup=returned hubGone=true
daemonGone=false`. Focused install-only reproduction then found the concrete cause: the current
staging-derived `forklight.sock` path is 113 UTF-8 bytes, while the installed macOS SDK declares
`sockaddr_un.sun_path[104]` including the terminating null. Hub intentionally reaches ready even
when its internal Daemon startup fails, so the next installed Daemon status and cleanup produce the
observed result.

The same packaged build passed both normal and immediate identity/stop sequences from a 93-byte
socket path. Main therefore admits the exact recovery at
`specs/m5-product-graduation/work-items/clean-bundle-short-runtime-home/spec.md`: move only the
ephemeral bundle `FORKLIGHT_HOME` to one unique owner-private OS temp root, enforce the Darwin byte
boundary before launch, stop owned processes before removing that exact root, and keep npm staging,
artifacts, publication, timeouts and global Daemon/Hub behavior unchanged. One new bundle is allowed
only after the normal quality chain and Integration; failure stops, while success continues the
already accepted installed real-delivery journey.

## Inputs and outputs

Inputs: one frozen source/build identity, a new bundle directory, isolated npm prefix and
`FORKLIGHT_HOME`, an installed tarball, an approved disposable sample project and a real healthy
Worker/Main path.

Outputs: `evidence/clean-clone-run.md`, the external `bundle-evidence.json`, Task/review/Integration
ids, setup/backup/restart observations and a functional-truth freeze for the Hub redesign.

## Required journey

1. Build one frozen clean bundle and verify its exact installed CLI/MCP/Daemon/Hub identity.
2. Use installed CLI/API only for readiness, setup facts, backup create/inspect and Main connection;
   do not edit the database or settings file.
3. Through the installed Main/ForkLight API, create or select one real bounded Task against a
   disposable project. A checked-in example may be selected but not edited to make it pass.
4. Let a real Worker produce a Candidate; run ForkLight independent acceptance and the accepted
   Judge policy.
5. Main reads the human result, records accept/revise/reject, and only an accepted exact Candidate
   proceeds through fresh preflight and safe Integration.
6. Restart the installed stack and prove the same Goal/Plan/Task, decision and delivery truth is
   still readable without duplicate execution or duplicate apply.
7. Record elapsed setup, first verified result and total delivery time. Exceeding a target is
   evidence for later design, not a Worker deadline.

The disposable project is copied once from the packaged `fixtures/checkout` artifact into the
external run root before Task submission. It is not edited to make verification pass. The real
Worker may change only its isolated Workspace; only the accepted exact Candidate may reach the
disposable source through normal Integration. The ForkLight source checkout is never the Task
project and must receive no A3 product change unless the blocker rule above is met.

The installed journey uses the packaged CLI/API for setup status, signed-in xAI selection, saved
`grok-4-6-xhigh`, Main MCP status/connection, backup preview/create/inspect, Task submission,
observation, Review Graph, Main review and delivery. Restore remains a temp-Home proof from A2; A3
does not replace the current real Home. One ordinary independent Judge is sufficient for the
disposable checkout behavior because this Task does not change ForkLight runtime, recovery,
security or durable schemas. Main still inspects the exact diff and integrates serially.

After delivery, restart only the installed isolated Daemon. Read the same Task, Main decision,
Review Graph and Integration history, rerun the disposable project's acceptance command, and
prove the delivered source was applied once. Observation timeouts never cancel or recreate the
Task. Repeated Task, Judge or Integration execution is forbidden unless a distinct accepted stop
decision explicitly admits it.

## Forbidden paths and non-goals

  human observation belongs to M5-C.
- A speculative product Candidate when the installed journey already passes; a new runner/entity,
  second status source, copied Runtime auth, source-checkout fallback or replay for a more favorable
  timing/result.

## Acceptance and verification

- Packaged prepack/full check, isolated install, CLI/MCP load, identity comparison and owned
  Daemon/Hub lifecycle pass.
- Installed setup and backup surfaces work in an isolated home and state their Keychain/Main-config
  limits honestly.
- One installed-product Task completes the full Worker → verification → Judge → Main → Integration
  chain against a disposable project, with no source-repo write before Integration.
- Restart preserves truth and does not duplicate work or apply.
- Evidence separates technical clean-install proof, current-user real delivery and the still-pending
  unfamiliar-human journey.
- The packaged fixture is unchanged before submission; the ForkLight source tree is unchanged by
  the disposable Task; the final project diff is applied exactly once through Integration.
- Timing records setup start/ready, Task submit, first independent verification and final delivery.
  No recorded target is used as a Task deadline or retry trigger.
- For the cleanup recovery, authoritative installed Daemon stop never triggers a second signal to
  a possibly reused PID; the fallback still removes a genuinely retained exact owned process and
  reports cleanup failure when it cannot.
