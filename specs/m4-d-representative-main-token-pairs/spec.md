# M4-D Work Item — Representative Main Token pair evidence

## User result

ForkLight's three graduated representative task families each have one auditable comparison where
the same Codex Main profile completes the same bounded work directly and through ForkLight, under
the same source base and acceptance. Only pairs that pass the M4 quality gate appear as Main Token
saving evidence.

## Background and current evidence

The M4 entry audit found zero valid pairs for `forklight-storage-lifecycle`, `worker-runtime` and
historical `hub-product-comprehension`. The current two legacy direct-Codex publications are
unrelated calibration task classes and cannot be reused as these pairs.

The Goal permits natural evidence or explicitly approved calibration and forbids replay merely to
improve rankings. 一骏's standing authorization covers this one bounded calibration per required
family. The comparisons exist solely to close the M4 exit evidence gap; they do not rank models,
change routing or authorize Hub work.

## `depends_on`

- M4-A, M4-B and M4-C are independently verified, reviewed, integrated and activated.
- A current Codex CLI Main profile with fixed model/effort can return complete terminal usage.
- Grok 4.6 Xhigh native Goal is launchable for the delegated Worker path.
- Main has prepared one content-identical source snapshot and one deterministic validator per
  family. No comparison begins from a drifting source.

## Comparison units

Run these three units serially:

1. **Storage lifecycle** — classify the current M3-C2 original/recovery/replacement Workspace
   dispositions and produce one bounded JSON decision artifact. It must distinguish protected
   reusable evidence from terminal regenerable space and use current storage audit/preview truth.
2. **Worker Runtime** — inspect the accepted M3-C2 Grok native Goal lineage and produce one bounded
   JSON truth artifact covering Runtime identity, Goal id/status/terminal, Attempt outcome,
   verification and Integration. It must not relabel the failed predecessor Goal as resumed.
3. **Historical Hub product comprehension** — read only the accepted historical Hub-labelled
   Task/routing evidence and produce one bounded JSON requirements artifact for future M5. It must
   state that no Hub/UI implementation or mutation occurred.

Each unit uses a Main-owned validator with a closed JSON schema, exact family name, required factual
references and privacy checks. The direct and delegated paths receive the same task text, inputs,
source snapshot, allowed output path and acceptance command.

## Execution and measurement

- **Direct side:** one isolated Codex CLI Main using `gpt-5.6-sol` at `xhigh` creates and validates
  the artifact without ForkLight Worker execution. The isolated source is never integrated into the
  real project. Capture its complete terminal usage as role `direct-main`.
- **Delegated side:** a separate isolated Codex CLI Main with the same model, effort, usage method
  and task contract uses ForkLight to admit one Grok 4.6 Xhigh native Goal Worker, supervise
  independent verification and two different-view Judges, make the Main decision and safely
  integrate into the comparison project. Capture that Main run as `delegated-main`; Worker usage,
  cost, elapsed time and corrections come from the ForkLight Task.
- Both samples bind to the delegated Task and one comparison id. Main performs the explicit M4-B
  assessment only after checking direct validation and delegated current delivery truth.
- One purposeful validation repair or Main correction may be used if it closes a concrete accepted
  gap; it is reported as cost. There is no model switch, Competition, third Judge, whole-unit replay
  or automatic replacement.

## Inputs

- the accepted unit contract and deterministic validator;
- one frozen source snapshot per pair;
- current read-only ForkLight Store/CLI evidence named by the unit;
- direct/delegated Main terminal usage events;
- delegated Task Worker/economics/delivery evidence;
- explicit pair assessment fields and evidence references.

## Outputs

- Three integrated bounded JSON artifacts under
  `goals/forklight-main-led-execution/evidence/m4-calibration/`, one per family;
- six complete Main usage samples, three accepted or explicitly rejected pair assessments, and
  three canonical family value-report projections;
- reviewed `goals/forklight-main-led-execution/evidence/main-token-pairs.json` generated from the
  canonical M4-C report;
- an exact decision packet instead of another run if any family cannot form a valid pair.

Direct Main runs write the same relative artifact path only inside their isolated comparison copy.
No product source, tests, Hub/UI or other Goal file is writable by a calibration Worker.

## Acceptance

1. Each pair has identical source base, scope, inputs, output path and acceptance command. Candidate
   source drift or different acceptance invalidates the pair.
2. Both Main sides use the same fixed Main profile and complete Codex terminal-counter method; no
   exchange-range substitution or missing-counter zero is allowed.
3. Direct artifact passes the same validator. Delegated artifact passes ForkLight independent
   verification, two different-view Judges, current Main accept and safe Integration in the
   comparison project.
4. M4-B assessment explicitly confirms same scope, same acceptance and delegated quality not lower.
   Otherwise the family is `cannot-determine` and no saving is claimed.
5. M4-C report separately shows direct/delegated Main Token, Worker Token, native-currency
   cost/range/unavailable, time, validation repair, Main correction/reverification and handoff
   counts.
6. The Hub-labelled unit reads historical evidence only; no Hub process, asset, UI, API mutation or
   design work occurs.
7. A pair is run once. One evidence-producing bounded correction is allowed; repeated failure,
   incompatible counters, scope drift or need for another replacement stops that unit.
8. `main-token-pairs.json` exactly matches the canonical value report and includes all three family
   results, including negative or unavailable evidence.

## Verification commands

For each side, run the same family validator plus `git diff --check` in its isolated source. For
each delegated Task also run its accepted ForkLight verification and Review Graph. At the M4
boundary run:

```text
npm run check
forklight health --json
forklight value-report --families '["forklight-storage-lifecycle","worker-runtime","hub-product-comprehension"]' --json
```

## Forbidden and non-goals

- No product code, test-count work, model leaderboard, routing update, automatic Competition,
  fallback model, third Judge or repeated calibration to seek a favorable number.
- No Hub/UI work before M5.
- No copying Provider credentials, reading private Codex history, raw prompt/response persistence or
  manual Token invention. Only terminal usage supplied by the measured Main process is accepted.
- No checksum/content-addressed coordination, lock, lease, version handshake or distributed
  protocol. The concrete same-source check exists only to prevent a wrong-base comparison.
- No Integration into the real project from the direct side. The delegated evidence artifact is
  integrated serially only after normal quality gates.

## Handoff and workspace disposition

Each measured Main hands off its usage event, validator result and exact artifact disposition. Each
delegated Worker/Review Graph hands off durable Task evidence through ForkLight. Preserve both
isolated copies until the pair assessment and canonical report are durable. Then reclaim direct
copies and terminal ForkLight Workspace/Runtime Home/cache through the accepted local storage
lifecycle; retain only count-only samples, assessments, compact artifacts and delivery references.

## Execution outcome — M4-D complete, M4 exit not met

All three serial units ran once. Storage has complete Main counts but no valid pair because only one
of two Judge opinions was schema-usable. Worker-runtime and historical Hub comprehension both have
valid same-scope/same-acceptance/non-lower-quality pairs and integrated byte-identical artifacts,
but delegated Main gross Tokens are respectively 2,401,089 versus 152,271 and 2,128,876 versus
119,202 direct. Neither is proven lower. No unit is replayed; canonical evidence and the M4 stop
decision are retained in the Goal evidence directory. Boundary build and 3,061/3,061 tests pass;
client/Daemon identity is matched, the live report exactly matches `evidence/main-token-pairs.json`,
and the pre-existing Hub observation is unchanged. Exact disposition:
`goals/forklight-main-led-execution/evidence/m4-boundary-stop-decision-packet.md`.
