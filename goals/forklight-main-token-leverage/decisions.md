# ForkLight Main Token Leverage — Decisions

Only durable decisions that change future work belong here. Append a new dated entry when a
decision changes; do not rewrite the confirmed Goal in contract.md.

## 2026-08-09 — North star

ForkLight exists to increase Main Token leverage while preserving delivery quality. Main
planning, decomposition, routing, review and judgment are high-value work and remain in scope.
Worker execution replaces Main research, implementation, testing and ordinary repair.

## 2026-08-09 — Work contracts are context-first and domain-neutral

Goal/Plan/Task must explain business and user background, parent work, prior decisions, inputs,
output use, authority, boundaries, quality and acceptance. Coding module/file details are an
optional domain extension, not the core contract.

## 2026-08-09 — Context-rich Tasks belong inside Plan and Goal

Version-3 context-rich Tasks are not standalone-only. Plan and Goal items must accept structured
version 2 or 3 contracts while continuing to reject legacy version 1. Outcome-intake Task
proposals follow the same rule. This is a compatibility extension, not a migration or new
workflow abstraction.

## 2026-08-09 — CLI/API before Hub

Core behavior must graduate through CLI/API and real Coding/non-Coding execution before Hub
redesign. Hub receives one unified Impeccable design pass after functional truth stabilizes.

## 2026-08-09 — Evidence and historical data

Old Tasks remain live only when they support fair routing or valid Main-Token comparison.
Create and verify a full backup before deletion. Review the dry-run first; permanently deleting
the backup requires separate approval.

The approved cleanup is now applied. Referential closure—not a flat eligibility flag—defines
the retained set, so judge, handoff, Competition, adaptation and paired-sample references remain
valid. Useful historical Tasks may be explicitly closed as `attention-resolved` when they no
longer require operational action; this preserves machine status and all quality, routing,
delivery, Token, cost and time evidence. Both verified backups remain retained.

## 2026-08-09 — Simplicity and bounded iteration

Use the simplest end-to-end implementation that meets current acceptance. New abstractions
require a current need or at least two real repeated cases. Non-blocking findings do not expand
the active Task. Stop when acceptance passes.

## 2026-08-09 — Milestone boundaries

Execution may continue automatically within an approved milestone. Crossing into the next
milestone requires a user-visible result and 一骏's confirmation.

## 2026-08-09 — M1 graduated at its boundary

M1 is complete after the final exit audit, real Coding and non-Coding dogfood, 2,847/2,847 full
tests, successful CLI/API boundary checks and matched CLI/Daemon build identity. This graduates
context-rich Goal/Plan/Task and CLI/API behavior only. It does not claim Main Token savings, does
not graduate persistent delivery, routing/value evidence or clean-clone, and does not authorize
Hub redesign. Work stops at this boundary until 一骏 confirms entry into M2.

Install reported three dependency audit findings (one moderate and two high). They are recorded
without an automatic dependency rewrite and belong to M5 dependency/security hardening unless a
new direct exploit path makes them an earlier blocker.

## 2026-08-09 — Quality limits are finite and evidence-driven

File, line, Token and duration limits guide scope and remain configurable; they do not override
delivery quality. Worker repair, Main correction and no-progress authority stay finite even when
time or Token ceilings are unset. One Worker validation repair and one Main correction are the
default ceiling; reaching it returns a decision instead of starting an endless loop.

## 2026-08-09 — Reuse before rerun; Competition remains exceptional

Retain proven Candidate paths and repair or hand off only the remaining gaps when evidence allows.
Do not restart an entire Task merely because one part failed. Competition or multiple judges are
used only for meaningful uncertainty, high-value alternatives or an explicit request; they never
replace Main judgment or become a default retry path.

## 2026-08-09 — Runtime truth and ForkLight dogfood

Codex, Claude Code and Grok Build are Runtime choices under the same Task authority. Use a Runtime's
native Goal only when ForkLight can prove and resume its real Goal/session identity; otherwise show
the actual single-run or persistent-session strategy. Meaningful ForkLight changes use ForkLight
for bounded implementation or review, while Main owns the contract, semantic review, correction
and Integration. Dogfood is evidence, not permission to create ceremonial Tasks or retries.

## 2026-08-09 — Publication remains separately authorized

Safe Integration into the local source tree may follow accepted Main review. Commit and push still
require 一骏's explicit approval.
