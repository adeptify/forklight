# ForkLight Main-led Execution — Decisions

Only durable choices that change future work belong here. The confirmed Goal contract is immutable;
execution changes are appended here and reflected in `plan.md` or `progress.md`.

## 2026-08-14 — One current Goal

`forklight-main-led-execution` is the only current project-management Goal. The prior
`forklight-main-token-leverage` Goal is archived with its M1 evidence and must not be maintained as
a second roadmap.

## 2026-08-14 — Parallelism requires orthogonality

Milestones are decomposed into existing Plan/Task records used as Work Items. A wave may execute
multiple Writers only when dependencies, interfaces, writable paths and validation surfaces are
independent. Default project capacity is up to three implementation Writers plus independent
review; settings and evidence may lower or raise it. Main integrates serially. No new Work Item
entity or coordination system is authorized.

## 2026-08-14 — Grok-first, capability-truthful execution

ForkLight development prefers Grok CLI 4.6 Xhigh after health and smoke proof. The current truthful
strategy is a ForkLight Goal contract plus resumable Grok persistent Session. It is not called
native Goal until ForkLight can prove the Runtime Goal identity, state, terminal and resume
contract. Runtime/model preference belongs in Worker Profiles, not universal product behavior.

## 2026-08-14 — Review Graph is a quality tool, not a loop

Meaningful delivery normally receives one independent read-only Judge; core Runtime, recovery,
concurrency, security, Integration and Token-accounting work normally receives two. At most three
are used for real unresolved disagreement. Judges do not edit or converse, and Main owns the final
decision. Unchanged evidence is not reviewed repeatedly.

## 2026-08-14 — Iteration follows evidence, not one fixed repair count

Attempt, correction, duration, Token and size limits are configurable circuit breakers. Work may
continue while it makes effective progress inside the accepted Spec. Acceptance ends the work;
repeated failure without new evidence, compensating patches, boundary expansion or invalid source
compatibility returns a decision packet to Main. Automatic model switching, whole-Task recreation,
extra Judges and Competition are not fallback loops.

## 2026-08-14 — Productize general behavior only

Cross-project behavior with understandable inputs/outputs, durable truth, configurable policy and
acceptance may enter ForkLight when required by the current Milestone or repeated in two real
cases. Runtime continuation, dependency waves, independent review, decision packets, partial reuse,
safe Integration, Task-space lifecycle, routing and value reporting qualify. Project preferences,
one-off recovery, documentation process and ceremonial self-proof do not.

## 2026-08-14 — Task space has a terminal disposition

Running, verifying, under-review and reusable-partial workspaces are protected. Terminal Tasks must
retain necessary audit/routing/Token evidence and reclaim regenerable workspaces, Runtime homes,
caches and orphan processes under an auditable policy. Destructive historical cleanup still
requires preview, integrity checks and explicit approval.

## 2026-08-14 — Publication remains separately authorized

Accepted local Integration may use ForkLight's safe path. Commit and push still require 一骏's
separate explicit approval.

## 2026-08-14 — Optimize for one local developer

ForkLight currently serves one local developer, not a team or distributed control plane. Do not
add checksums, content addressing, locks, leases, version handshakes or repeated validation for
hypothetical multi-user coordination. Retain only minimal checks tied to a concrete failure:
durable-data corruption, unreadable protocol/schema, Candidate base mismatch or unsafe
Integration. Local path ownership plus serial Main Integration is the default coordination model.

## 2026-08-14 — Development timeouts are safety breakers, not delivery clocks

Development Work Items default to no absolute wall-clock deadline or Token ceiling; file and line
limits remain warnings unless a concrete failure requires a hard boundary. A Main observation,
poll, transport or console timeout ends only that observation call and never changes the durable
Task/Attempt state. Independent acceptance commands use a 30-minute per-command timeout locally so
normal builds and focused suites are not cut off by the former five-minute window. Any future hard
time limit must name the exact cost, Provider or runaway-process failure it prevents and include a
focused verification case. Every currently saved local Worker Profile now explicitly sets
`noProgressTimeoutMs: null`; the global 30-minute value remains only a legacy/unprofiled fallback,
not the policy of a selected development Worker.
